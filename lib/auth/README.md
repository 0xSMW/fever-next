# Authentication implementation notes

Authentication uses the single-owner model described below. Setup and recovery operations are documented in [the operator guide](../../docs/OPERATIONS.md).

The owner password uses Node's native scrypt with N=131072, r=8, p=1, a random 16-byte salt, and a 64-byte derived key. The versioned stored encoding accepts only these bounded parameters. This is the portable password-hashing alternative to a native Argon2 dependency. Each derivation uses about 128 MiB, and each web process allows two concurrent derivations and at most eight queued requests. PostgreSQL throttling runs before browser password work and works across web processes. The reverse proxy should also limit request rates, connections, body size, and request time.

New passwords require at least 12 characters and at most 1,024 UTF-8 bytes. Imported hashes may represent passwords up to 4,096 bytes without changing their bytes or enforcing the new minimum. Neither new passwords nor imported password bytes are trimmed or Unicode-normalized. Legacy PHP trimmed submitted browser passwords before comparison; new browser entry uses the exact entered password. Login email lookup trims and lowercases the entered address, while the stored original email remains available for the exact legacy API digest. New or changed emails receive additional syntax validation.

The Fever v3 credential remains the lowercase MD5 of the exact stored email, a colon, and password bytes. Only a SHA-256 verifier of that digest is persisted. MD5 is required by the client protocol and is never used as a password-storage hash. Incoming digest hex is case-insensitive, and verifier comparison uses constant-time comparison. Changing the email or password atomically replaces the verifier, revokes every browser session, and invalidates outstanding recovery tokens. Recovery requires a different password so a compromised old deterministic digest becomes unusable. Logout-all revokes browser sessions and recovery tokens while leaving the separately managed Fever API credential usable.

NextAuth credentials use encrypted JWT sessions without an ORM adapter. Each token records the owner ID, auth epoch, fixed authentication deadline, and canonical installation URL. Both the NextAuth session callback and server authorization guards check the current database epoch and active installation. The default session lifetime is seven days, configurable from five minutes to 30 days; polling a session never extends its original authentication deadline. The legacy reader `session_timeout` preference has no effect on login lifetime. Browser owner contexts retain their checked epoch privately for a second service-boundary check; callers should pass the returned context directly rather than reconstructing it from an ID.

The web configuration requires `FEVER_BASE_URL`, `NEXTAUTH_URL` equal to that base followed by `/api/auth`, an independent random `NEXTAUTH_SECRET` of at least 32 bytes, and `NEXT_PUBLIC_BASE_PATH` matching any URL prefix. HTTPS is required except for loopback development outside production. The reverse proxy must preserve the canonical public request origin and base path. Session and CSRF cookies are HTTP-only, scoped to the installation path, and secure on HTTPS. The session cookie uses SameSite=Lax; the application CSRF cookie uses SameSite=Strict. Cookie names include an installation URL hash. JWT and CSRF signatures also bind the canonical installation URL.

Browser API flow:

1. Fetch `GET /api/session` with same-origin credentials. Its no-store response contains `configured`, `authenticated`, `csrfToken`, and, when signed in, the owner ID and email.
2. Send that token as `X-Fever-CSRF` for modern mutations, including setup and recovery. The server requires the matching signed, HTTP-only cookie, the canonical Origin, and a same-installation Referer when supplied. Tokens expire after an hour and bind the current auth epoch. Fetch the session again after sign-in or an expired-token response.
3. Use `next-auth/react` signIn/signOut under the configured `/api/auth` base. NextAuth retains its own CSRF token protocol; its mutation route additionally checks origin and bounds the request body.
4. `POST /api/session` with `{ "action": "logoutAll" }` revokes all browser sessions. Clients must return to sign-in after this response or an account update.

Setup requires the operator's random `FEVER_SETUP_TOKEN` of at least 32 bytes and a configured active feed-encryption key. It creates the single owner, API verifier, preferences, navigation defaults, and sharing-service defaults in one transaction. Insertion and locking of the singleton installation row serialize competing setup requests. `setupClosed` is permanent: deleting an owner or preserving an uninstalled tombstone cannot reopen setup. The stored URL must match the configured canonical URL. The setup token can be removed from the deployment environment after initialization.

Every account, setup, recovery, and logout-all transaction takes the shared installation advisory lock before row locks. Operator quiescing takes the exclusive lock for the same `fever:installation` key. Recovery is unavailable while the installation is in maintenance or uninstalled. Auth changes append a redacted operation journal record in the same transaction. Those records contain epochs and event metadata, never passwords, hashes, API verifiers, or raw recovery tokens. Credential events flag the need for operator credential reconciliation during rollback: the secure target cannot reconstruct a plaintext legacy password from its hash.

The local recovery CLI imports `issueRecoveryToken({ ttlMinutes? })` from `lib/auth/recovery.ts`. It returns the raw token once and its expiry; it never returns an existing password. The default lifetime is 15 minutes, with a one-to-30-minute bound. Issuance invalidates earlier outstanding tokens. The database stores a purpose-bound SHA-256 verifier of 256 bits of random token material. Consumption checks expiry and epoch and marks the token used atomically with password/API rotation. Recovery issuance has no HTTP endpoint and does not send mail. Operator tooling should display the token once and avoid persistent logs, URL query parameters, and analytics.

Authentication rate buckets contain keyed fixed subject names, counts, and expiry timestamps, with no email or trusted-forwarded-IP assumption. Limits are 12 login, five setup, eight recovery, ten account-verification, and 1,200 Fever API attempts per minute per installation. `pruneAuthRateLimits()` removes expired buckets during worker housekeeping. Global single-owner throttling deliberately prioritizes a bounded workload; a trusted reverse proxy can add stricter per-client limits without accepting caller-controlled forwarded addresses in the application.

Authentication regression coverage should include correct and incorrect credentials, imported-byte fixtures, installation races, one-time-token races and expiry, credential-change concurrency, logout-all, fixed session expiry, wrong-origin/base-path requests, CSRF rotation, proxy origin handling, NextAuth cookies and sign-out, rate limits across processes, and the selected pinned framework/authentication versions.
