# PostgreSQL migrations

The current release schema is **2**. [manifest.json](manifest.json) records the reviewed SQL filenames, versions, and SHA-256 checksums. [0000_initial.sql](0000_initial.sql) creates the initial schema; [0001_items_feed_navigation.sql](0001_items_feed_navigation.sql) adds the ordinary B-tree `items_feed_navigation_idx(feed_id, read_at, is_saved)`.

## Apply or inspect migrations

Run commands from the repository root with a private, explicitly selected environment file. Use a direct PostgreSQL connection or session pooling: the runner holds a session advisory lock, so transaction poolers are unsuitable. A migration role should own DDL permissions; the application role needs only its reviewed table and sequence privileges. See the [operator guide](../docs/OPERATIONS.md) for environment, TLS, and role configuration.

```sh
pnpm ops inspect-target --env-file /etc/fever/operator.env --target-url-env MIGRATION_DATABASE_URL
pnpm db:migrate status --env-file /etc/fever/operator.env --target-url-env MIGRATION_DATABASE_URL --target-fingerprint TARGET_SHA256
pnpm db:migrate apply --env-file /etc/fever/operator.env --target-url-env MIGRATION_DATABASE_URL --target-fingerprint TARGET_SHA256 --confirm migrate:TARGET_SHA256
```

Replace `TARGET_SHA256` with the fingerprint returned by `inspect-target`. The runner verifies the selected target, all SQL checksums, and the complete applied ledger. It acquires a dedicated-connection advisory lock and applies one transaction per reviewed version. A failed transaction rolls back both DDL and its ledger entry. Inspect the failure and rerun the same reviewed release after correcting the cause.

Application and worker startup never apply migrations. Do not use schema push. The schema 2 index is created transactionally, without `CONCURRENTLY`; schedule an appropriate quiet-write window for an existing installation.

## Change the schema

Keep [lib/db/schema.ts](../lib/db/schema.ts), reviewed SQL, the manifest, and migration metadata consistent. Applied SQL and its journal entry are immutable: never edit an already applied migration or reinterpret its version. Add a new reviewed migration for subsequent changes. Establish the actual applied baseline before generating a diff; a fresh install alone does not verify a sequential upgrade.

The `installation` singleton is a permanent setup latch. Setup creates owner ID `1` and closes the latch. Uninstall retains the latch and authentication tombstone, revokes credentials, and keeps setup closed. Maintenance backups intentionally have no owner foreign key so recovery records remain available.

IDs, foreign keys, legacy epoch seconds, and CRC32 values use PostgreSQL bigint. Checks bound values to JavaScript's exact integer range; CRC32 and legacy link weight are limited to unsigned 32-bit values. Raw `pg` results retain bigint strings. Convert explicitly with [lib/db/numbers.ts](../lib/db/numbers.ts); do not install a global bigint-to-number parser. Audit, lease, recovery, and job clocks use UTC `timestamptz`. An unread item's `read_at` remains exactly `0`.

Imports preserve explicit IDs using `GENERATED BY DEFAULT` identity columns. The importer reconciles every identity sequence under its exclusive import lock before new writes, including reserved quarantined IDs. Empty sequences retain their initial state and advanced sequences never move backwards. Preserve undecodable or NUL-containing source bytes in restricted archives rather than inserting invalid PostgreSQL text.

Hashes bound unique keys for long URLs and identities. Full values remain available for collision checks; CRC32 is compatibility metadata and never the sole uniqueness constraint. Imported collation-sensitive text follows the explicit policy in the [compatibility specification](../docs/NEXTJS_MIGRATION_SPEC.md); PostgreSQL's default collation is not assumed to match MySQL `utf8_unicode_ci`.

## Restore an older archive

The restore tool accepts a known, checksum-reviewed migration prefix. A schema 1 archive restored by release 2 reports `restoredSchemaVersion: 1`, `releaseSchemaVersion: 2`, and `requiresMigration: true`. It keeps the installation in maintenance, leaves setup closed, and does not apply upgrades or activate. Unsupported versions, changed hashes, divergent installation versions, and extra or missing ledger rows fail closed.

1. Restore into an empty destination using the approved archive digest and inspected target fingerprint. Keep the archive, restore receipt, and encryption keys protected.
2. Reinspect the destination, run `db:migrate status`, and review pending SQL.
3. Run the separate `db:migrate apply` command with the required fingerprint and confirmation.
4. Run `status` again. Verify schema/ledger, content, sequences, separately restored keys, browser and Fever API credentials, and required recovery assertions. Reapply runtime grants because restore archives omit ownership and privileges.
5. Activate only through the explicit evidence-backed workflow in the [operator guide](../docs/OPERATIONS.md#freeze-and-activation).

The historical restore result can continue to record `requiresMigration`; the migration runner determines the current pending status. Use PostgreSQL client tools with the same major version as the server. See [testing](../tests/README.md) for the optional database integration checks.
